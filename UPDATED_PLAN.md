# Implementation Specification: Volunteer Attendance System

## 1. Objective

Build a QR-based volunteer attendance system for an organization that conducts multiple activities and sessions at different physical locations, primarily on weekends.

The system must allow any registered, active volunteer to check in to an eligible session by scanning a **printed, static QR code displayed at the venue**.

The system records only:
- Which volunteer attended which session.
- The server-recorded date and time of their tap-in.

Do not implement employee-style attendance, payroll, mandatory volunteer assignments, working hours, or automatic absence tracking.

## 2. Core Product Principles

1. Attendance is session-based, not employee-day-based.
2. Any registered, active volunteer can attend any session that permits general volunteer participation.
3. Each venue has a reusable, printed QR code.
4. A venue QR identifies the venue; it does not authorize attendance by itself.
5. A volunteer can have only one attendance record per session.
6. A volunteer may attend multiple sessions on the same day, generating a separate record for each session.
7. Attendance timestamps must be generated by the server.
8. Closed and cancelled sessions must reject ordinary check-ins.
9. All administrative corrections must be auditable.
10. Do not create missing-attendance records for volunteers who did not attend.

## 3. User Roles

### Volunteer
- Register and sign in.
- Scan a venue QR code.
- View the venue and eligible sessions.
- Select a session and confirm attendance.
- View successful check-in confirmation.
- View personal attendance history.

### Administrator
- Manage volunteers.
- Create and manage venues.
- Generate, download, print, revoke, and replace venue QR codes.
- Create, publish, open, close, reopen, and cancel sessions.
- View session attendance in real time.
- Search attendance records.
- Correct attendance records with a mandatory reason.
- View volunteer participation history.
- Export session attendance reports.
- Review an audit log of administrative actions.

## 4. Venue QR Code Lifecycle

Each venue must have a unique, reusable QR code.

### QR generation
- Generate a QR code when a venue is created.
- Encode a URL such as `https://your-domain.example/check-in/v/{opaque-venue-id}`.
- Use a unique, non-sequential venue identifier.
- Do not encode volunteer credentials, session permissions, or reusable authentication secrets.
- Allow the admin to download and print the QR code.
- Display the venue name and basic instructions alongside the QR.

### QR usage
- A volunteer scans the printed QR code.
- The QR opens the venue-specific attendance page.
- The backend verifies that the venue exists, is active, and has a valid QR configuration.
- The system identifies sessions currently accepting check-ins at that venue.

### QR revocation
- Admins can revoke a venue QR if it is compromised or the venue is deactivated.
- Revoking a QR must immediately prevent new check-ins through that code.
- Admins can generate and print a replacement.
- Existing attendance records must not be deleted when a QR is revoked.

The QR is a venue identifier, not proof that a volunteer is physically present. Do not claim that static QR scanning alone prevents proxy attendance.

## 5. Session Lifecycle

Implement the following session states:

- `DRAFT`: Session is being created or edited; unavailable for check-in.
- `SCHEDULED`: Session is published but its check-in window has not opened.
- `OPEN`: Session is accepting attendance.
- `CLOSED`: Ordinary check-ins are no longer accepted.
- `CANCELLED`: Session has been cancelled and cannot accept attendance.
- `ARCHIVED`: Session is retained for historical reference.

### Session fields
- Session ID.
- Activity title.
- Optional description.
- Venue ID.
- Scheduled start time.
- Scheduled end time.
- Check-in opening time.
- Check-in closing time.
- Session status.
- Created by.
- Created and updated timestamps.

### Session rules
- Each session belongs to exactly one venue.
- A venue can host multiple sessions.
- Multiple sessions at the same venue may overlap.
- The admin can publish, cancel, close, and reopen sessions according to their permissions.
- Automatically open sessions at their configured check-in opening time.
- Allow authorized admins to open a session early.
- Allow admins to close sessions manually.
- Optionally auto-close sessions at a configured fallback time.
- Closed sessions can be reopened only by an authorized admin.
- Cancelled sessions cannot accept new attendance.
- Archiving must preserve all attendance and audit records.

### Default timing
Use these as configurable defaults:
- Check-in opens 15 minutes before the scheduled start.
- Check-in closes 60 minutes after the scheduled start.
- Admins can adjust these values per session.
- Use the venue's configured time zone for session scheduling.
- Store timestamps in UTC and convert them for display.

## 6. Volunteer Check-In Workflow

Implement this exact workflow:

1. Volunteer scans the printed venue QR code.
2. The system opens the venue-specific attendance page.
3. If the volunteer is not authenticated, require sign-in and then resume the check-in flow.
4. Validate that the venue exists, is active, and has not had its QR revoked.
5. Fetch sessions at that venue that are currently accepting check-ins.
6. If no sessions are available, show: "There are no activities currently accepting attendance at this venue."
7. If one session is available, preselect it.
8. If multiple sessions are available, display a session selection screen showing:
   - Activity name.
   - Venue.
   - Scheduled start and end times.
   - Any short description needed to distinguish activities.
9. The volunteer selects the correct session.
10. Display a confirmation screen identifying the selected activity and venue.
11. The volunteer presses "Confirm attendance."
12. The backend revalidates the session, venue, volunteer account, QR configuration, and check-in window.
13. If valid, create the attendance record using the server timestamp.
14. Return a success response and show the activity name, date, venue, and tap-in time.
15. If the volunteer has already checked in, return the existing record and its original timestamp instead of creating a duplicate.

The frontend must never display a successful check-in until the backend confirms it.

## 7. Attendance Data and Rules

An attendance record must contain:

- Attendance record ID.
- Session ID.
- Volunteer ID.
- Server-generated `tapped_in_at` timestamp.
- Source, such as `QR` or `ADMIN`.
- Creator or actor ID where applicable.
- Creation and update timestamps.

### Database constraints
- Enforce a unique constraint on `(session_id, volunteer_id)`.
- Use foreign keys for session and volunteer relationships.
- Reject attendance for inactive volunteers.
- Reject attendance for invalid venues, revoked QR codes, closed sessions, and cancelled sessions.
- Reject ordinary check-ins outside the configured check-in window.
- Generate timestamps on the server.
- Use transactions and idempotent request handling to prevent duplicate records during retries or concurrent requests.

Do not store a daily attendance status for every volunteer. A volunteer who did not attend simply has no attendance record for that session.

## 8. Admin Attendance Dashboard

Provide a session-focused dashboard.

### Session list
Show:
- Activity name.
- Venue.
- Date and time.
- Session lifecycle status.
- Number of volunteers checked in.
- Quick actions to view, edit, close, cancel, or manage the session.

Include filters for date range, venue, activity name, and session status.

### Session detail page
Show:
- Activity details.
- Venue and scheduled times.
- Current session status.
- QR status and QR management actions.
- Total unique volunteers checked in.
- Searchable attendance list.

Each attendance row should show:
- Volunteer name.
- Volunteer identifier.
- Tap-in time.
- Record source.
- Available administrative actions.

Do not show "absent volunteers" or "not checked in" for the general volunteer directory. Volunteers are not assigned mandatory attendance obligations.

### Manual corrections
- Require an explicit reason for each correction.
- Record the admin's identity and timestamp.
- Preserve the original timestamp and values in the audit history.
- Do not silently overwrite historical data.
- Apply the same duplicate and session-consistency constraints to manual records.

### Reports and exports
Allow admins to export session attendance as CSV, including:
- Activity name.
- Session date.
- Venue.
- Volunteer name.
- Volunteer identifier.
- Tap-in timestamp.
- Record source.

Also provide a volunteer history page listing all sessions attended by that volunteer.

## 9. Security and Reliability

Implement the following controls:

- HTTPS for all production requests.
- Authentication and authorization on every protected endpoint.
- Role-based access control for administrative functions.
- Server-side validation for every attendance submission.
- Rate limiting for repeated failed requests.
- QR revocation checks.
- Database uniqueness constraints and transaction-safe attendance creation.
- Idempotent retries for network timeouts.
- Audit logs for session changes, QR revocation, attendance corrections, and administrative actions.
- Safe handling of expired sessions and invalid venue identifiers.
- No secrets or authentication credentials embedded in QR codes.
- Do not trust client-provided timestamps or session statuses.

### Network failures
If the network is unavailable, do not claim attendance has been recorded. Show a clear retry option or direct the volunteer to an admin-assisted process.

If the server saves attendance but the response times out, a retry must return the existing record rather than create another one.

### Static QR limitations
A printed QR can be photographed and shared. Authentication and QR validation do not prove physical presence.

Keep the MVP simple. Additional verification, such as supervised check-in, can be considered later if the organization needs stronger protection against proxy attendance.

## 12. Error Handling

Return clear, actionable responses for:

- Unauthenticated volunteer.
- Inactive volunteer account.
- Unknown or deactivated venue.
- Revoked QR code.
- No currently available sessions.
- Invalid session selection.
- Session not yet open.
- Session closed or cancelled.
- Duplicate check-in.
- Network timeout or server error.
- Unauthorized administrative action.

For duplicate check-ins, return the existing attendance record as a successful, idempotent outcome.

For other validation failures, do not create an attendance record.

## 13. Acceptance Criteria

The implementation is complete when all of the following are verified:

1. An admin can create multiple venues.
2. Each venue has a printable, reusable QR code.
3. Revoking a venue QR immediately blocks new check-ins through that code.
4. An admin can create multiple sessions at different venues.
5. Multiple sessions can exist at the same venue, including overlapping sessions.
6. A registered volunteer can scan a venue QR and select an eligible session.
7. An unauthenticated volunteer must authenticate before attendance is recorded.
8. A successful tap-in records the server timestamp.
9. Scanning twice for the same session does not create duplicate attendance.
10. The same volunteer can attend two different sessions on the same day.
11. Sessions reject ordinary tap-ins before their check-in window and after closure.
12. Cancelled sessions reject new attendance.
13. Network retries do not create duplicate records.
14. Admins can view attendance and export session reports.
15. Volunteers can view their own attendance history.
16. Manual corrections require a reason and generate an audit record.
17. A volunteer who does not attend has no attendance record; no absence record is created.
18. QR scans, venue identifiers, and client-provided timestamps cannot bypass server-side validation.

# Extension: International Event Participant Access Portal

## 15. Objective and Scope

Extend the existing application with an administrator portal for managing access to a large international event (approximately 5,000 participants). The event participant list is supplied by organizers and may contain participants from many countries. The list initially contains each participant's name, country, and email address.

The portal must support importing participant records, issuing printable QR passes, scanning passes at entry and exit gates, allowing exit and re-entry using the same valid pass, handling exceptions, and reporting current occupancy and access history.

This is an extension of the existing project, not a separate application or database. Use the same application, authentication/authorization conventions, database instance, migration system, and UI patterns wherever practical. Do not break or change the existing volunteer session-attendance workflows.

### Important distinction: shared database, distinct record types

- Keep international event participants in a dedicated `event_participants` table in the **same database** as the existing `volunteers`, `locations`, `sessions`, and `attendance_records` tables.
- Do not force every event participant to be a volunteer or create volunteer accounts for them.
- Do not combine volunteer session attendance with event gate entry/exit history. They represent different activities and must remain separate.
- If a person is independently both a volunteer and an event participant, an optional explicit link between records may be supported later. Do not automatically merge people solely because their names or email addresses look similar.
- Use additive database migrations. Preserve all existing records and behavior.

## 16. Event Access Roles

### Event administrator
- Import participant lists from CSV; support XLSX if the existing stack already has a suitable library.
- Preview and validate imports before committing them.
- Review likely duplicates and import errors.
- Search, view, and update participant records.
- Generate, issue, resend, revoke, and replace participant QR passes.
- Trigger or retry pass emails and inspect delivery status.
- Configure the event, its gates, and entry/exit mode for scanning stations.
- View live occupancy, access events, exceptions, and reports.
- Perform authorized manual corrections with a mandatory reason and audit trail.

### Gate operator
- Sign in to an authorized scanning station.
- Operate that station in a configured `ENTRY` or `EXIT` mode.
- Scan a printed participant pass and see an unambiguous accepted/rejected result and the participant's name.
- Refer invalid, duplicate, revoked, or otherwise exceptional cases to the staffed exception desk.
- Must not be able to change participant data, issue credentials, or alter history unless separately authorized.

### Exception-desk operator
- Search participants by registration reference, name, or email.
- Resolve lost, damaged, or unavailable passes according to event policy.
- Verify the participant using the organization's approved procedure before reprinting or replacing a pass.
- Record the reason and operator for all manual interventions.
- Escalate unknown participants or conflicting records; do not silently create unrestricted access for someone not on the approved list.

Enforce authorization on the backend, not only by hiding UI controls.

## 17. Participant Import and Management

### Import workflow
1. An authorized admin uploads a CSV (and optionally XLSX) file.
2. Show a preview and map source columns to `name`, `country`, and `email`.
3. Validate required values, email format where practical, file size, and supported encoding. Preserve Unicode names and country names.
4. Normalize email addresses for comparison without altering the participant's display name.
5. Identify exact duplicate emails and likely duplicate people for review. Do not automatically merge records based only on similar names.
6. Display row-level validation errors and an import summary before the admin confirms the import.
7. Make imports safe to retry: do not create duplicate participants or credentials if the same file is uploaded again. Provide a clear policy for whether existing records are updated, skipped, or flagged for review.
8. Keep an import summary/audit record, including actor, timestamp, counts created/updated/skipped, and errors. Avoid storing unnecessary copies of uploaded personal data.

### Participant directory
Provide searchable, paginated participant management with filters for country, pass status, and current in/out state. Show participant name, country, email, registration reference, credential status, current event state, and relevant timestamps. Restrict access to personal data to authorized roles.

Assign every participant a stable internal ID and a human-readable, non-secret registration reference. Do not expose sequential database IDs as authorization tokens.

## 18. QR Pass Issuance and Email

- Generate a unique, cryptographically random, unguessable opaque credential for each participant.
- The QR must contain only an opaque credential or URL containing that credential. Never encode the participant's name, email, country, or other personal data directly in the QR.
- Store a secure hash of the credential where feasible, rather than storing the raw token in the database. Ensure token entropy is sufficient to prevent guessing.
- Map each credential to one participant and one event. Enforce uniqueness and active/revoked status server-side.
- Generate a printable pass (PDF or print-friendly web page) containing the event name, participant name, country if appropriate, registration reference, QR code, venue instructions, and lost-pass instructions.
- Email the personalized pass to the email address supplied in the organizer's list. Support retries and show delivery status/errors to admins.
- Do not require participants to create accounts or complete OTP verification merely to receive a pass when the organizer's approved list is the source of registration. If participants are allowed to claim or change a registration, verify email ownership and audit the change.
- Explain that the QR is a bearer credential and can be copied or shared. Gate operators should see the registered name after scanning and follow the event's identity-verification policy for suspicious cases.
- Replacing a pass must revoke the old credential and issue a new one for the same participant. Preserve historical access events and audit the replacement.
- A revoked credential must be rejected immediately by online scanners.

## 19. Entry, Exit, and Re-entry Workflow

Participants are expected to bring **printed passes**; do not make possession of a phone or use of a participant mobile app a requirement.

1. Admin imports and reviews the approved participant list.
2. Passes are issued and emailed sufficiently before event day so participants can print them.
3. At a gate, an operator scans the QR from the printed pass using the gate's scanning device.
4. The backend validates the credential, event, participant status, gate authorization, and current admission state.
5. If the station is in `ENTRY` mode and the participant is currently `OUTSIDE`, record an accepted entry and transition them to `INSIDE` atomically.
6. If the station is in `EXIT` mode and the participant is currently `INSIDE`, record an accepted exit and transition them to `OUTSIDE` atomically.
7. After an accepted exit, the same active QR can be used for a later entry. Do not permanently invalidate a credential after its first scan.
8. If a participant scans at entry while already `INSIDE`, reject the duplicate entry without changing state. If a participant scans at exit while already `OUTSIDE`, reject the invalid exit without changing state. Display clear operator instructions for both cases.
9. Invalid, unknown, revoked, inactive, or wrong-event credentials must not change admission state.
10. The UI must not claim a scan succeeded until the backend confirms it.

Use explicit entry/exit mode configured for each scanning station; do not infer whether a scan is an entry or exit from the participant's state alone. Display the gate/station name and mode prominently to reduce operator error.

### Event state and occupancy

- Track each participant's current event state as `OUTSIDE` or `INSIDE` for this event.
- Derive total current occupancy from participants whose current state is `INSIDE` and display it on the admin dashboard.
- Keep entry/exit events as an append-only history. Current state may be stored for performance, but every accepted state transition and state update must be committed in the same database transaction.
- Treat accepted entry/exit events separately from rejected scan attempts. Rejected attempts may be logged for security and operational diagnostics, but must not affect occupancy.
- Provide a controlled correction workflow if a scan was accepted but the participant did not actually cross the gate. Require an authorized operator, reason, and audit entry; never silently erase the original event.

## 20. Gate Dashboard and Exception Handling

### Gate scanning screen
- Large, high-contrast scan status suitable for quick use at a busy gate.
- Clear `ENTRY` or `EXIT` indicator, gate/station name, and operator identity.
- Show participant name and registration reference on a valid scan; show accepted entry/exit outcome and current state.
- Give clear messages for already inside, already outside, invalid QR, revoked pass, inactive participant, network failure, and server error.
- Avoid exposing participant email or other unnecessary personal information to gate operators.
- Prevent accidental repeated submission while a scan is processing, while retaining server-side idempotency and transaction safety.

### Exception desk

- Handle missing/forgotten/damaged printouts, email delivery problems, duplicate records, and approved registration corrections.
- Reprint or replace passes only after the organization's identity-verification procedure is followed.
- Log operator, action, timestamp, reason, and affected participant.
- Any emergency/manual admission must be explicitly authorized, recorded as a distinct source, and included in reports and audits.

## 23. Reliability, Security, and Operations

- Require HTTPS in production, authenticated admin/operator accounts, and role-based access control.
- Use cryptographically secure, opaque QR credentials; never include personal information or authorization data in plain text in the QR.
- Validate event status, credential status, participant status, gate status/mode, and current state on the server for every scan.
- Use an atomic database transaction for each accepted entry/exit, including state transition and event-history write.
- Use idempotency keys or equivalent retry protection so a timeout/retry cannot create duplicate accepted events.
- Serialize concurrent transitions for the same participant so two scanners cannot both act on stale state.
- Store timestamps in UTC and display them in the event's configured time zone.
- Rate-limit invalid scans and protect participant search and import endpoints from abuse.

Do not let independent offline scanners independently accept entry, because they cannot reliably prevent conflicting or duplicate admission across gates. Any future offline mode must be designed explicitly with durable local logs and a reconciliation strategy.

- Rehearse gate throughput with representative hardware and staffing before event day. Provide multiple scanning lanes and a separate exception desk; final lane count should be based on timed trials and arrival/departure patterns rather than an assumed universal throughput.

## 26. Open Events: Advance Registration and Walk-In Attendance

### Objective

Support a third workflow for events attended by hundreds of people where some attendees register in advance and many others may arrive without registering. The system must create an attendance record for every person who is admitted, while keeping entry fast and supporting different levels of identity assurance for different events.

This is distinct from:
- volunteer session attendance using a reusable venue QR code; and
- pre-imported international participant access using individual printable QR passes and entry/exit tracking.

Implement this as an event-registration/check-in module within the existing application and database, not as a separate application.

### Core principles

1. Every admitted attendee must have an event-specific registration record and a recorded check-in.
2. Support both `ONLINE` advance registration and `WALK_IN` registration at the venue.
3. A registration, a contact-verification result, an identity-verification result, and an attendance/check-in record are different facts; never treat one as proof of another.
4. Do not require a participant to have a smartphone. Staff must be able to register a walk-in and print a badge/pass or provide a registration reference.
5. Do not require a full account signup for public-event attendees unless a specific feature requires an account.
6. Make identity assurance configurable per event. Open community events may use basic registration; events needing stronger assurance may require verified contact details or an in-person ID check.
7. Collect the minimum personal data needed for the event's stated purpose. Do not collect or retain copies of identity documents by default.
8. A QR credential is a lookup credential, not proof of the holder's real-world identity. It must contain only a random, opaque identifier and must not encode personal information.
9. Check for likely duplicate registrations before creating a new one, but do not automatically merge people based only on similar names or shared household/contact details.
10. Every manual override, verification decision, and correction must be auditable.

### Event configuration

Each event should configure:
- Event name, date/time, venue, time zone, and capacity if applicable.
- Whether advance registration is enabled.
- Whether walk-ins are allowed and whether registration can be paused when capacity is reached.
- Required attendee fields (default: name and one contact method where practical; allow a documented minimal-data policy for events where contact details are not necessary).
- Whether email or phone contact verification is optional or required.
- Identity assurance policy: `BASIC_REGISTRATION`, `CONTACT_VERIFIED`, or `IN_PERSON_ID_CHECK`.
- Whether photo ID checks are mandatory, conditional, or not used.
- Whether attendees may leave and re-enter; if so, enable entry/exit state tracking.
- Whether badges or paper QR passes should be printed at check-in.

The selected policy must be visible to administrators and staff before the event opens. Do not require the strictest verification level for every event by default.

### Advance-registration workflow

1. Attendee submits the public registration form.
2. Validate required fields and search for a possible existing registration for this event.
3. Create an event registration with source `ONLINE` and a unique registration reference.
4. If the event's policy requires contact verification, send a single-use email link or OTP and record whether verification succeeded. Explain that this proves access to the email address or phone number, not legal identity.
5. Issue an opaque QR credential when appropriate and send a confirmation/pass by email. Do not expose the credential token in logs or analytics.
6. At the venue, staff scans the QR, checks the result, and completes any identity check required by that event's policy.
7. Record check-in only after the backend accepts the operation.

### Walk-in workflow

1. Provide a dedicated walk-in registration station separate from the fast lane for already-registered attendees.
2. Staff searches the current event's registrations using registration reference, name, email, or phone as permitted. Use case-insensitive and Unicode-aware matching where feasible.
3. If a likely existing registration is found, staff verifies enough details to avoid creating a duplicate and continues with that registration.
4. If no match exists, staff creates a registration with source `WALK_IN`, collects only the fields required by the event policy, and receives a unique registration reference.
5. Issue a QR credential and optionally print a badge or paper pass. A phone and personal email address must not be universally mandatory; support a documented fallback for attendees who lack them.
6. Complete the configured verification steps, then record the attendee's check-in.
7. If the event has reached capacity or walk-ins are disabled, show a clear rejection/escalation workflow; do not silently admit the person without recording the exception.

### Identity and contact verification

Store the verification method and outcome explicitly. Suggested states:
- `NOT_REQUIRED`
- `PENDING`
- `CONTACT_VERIFIED`
- `ID_CHECKED`
- `FAILED`
- `OVERRIDDEN` (requires authorized staff and a reason)

These states are not interchangeable. A contact OTP/link confirms access to a contact channel; it does not confirm the attendee's legal name. An in-person ID check records that an authorized staff member inspected an accepted document according to event policy; do not store document images or document numbers unless a documented legal/security requirement justifies it.

For an event requiring stronger assurance, staff should compare the attendee with the accepted ID and record the check result, verifier, and timestamp. If verification fails, route to a supervisor/exception desk rather than silently bypassing the policy. Any permitted override must capture an actor, reason, and timestamp.

### Check-in and re-entry

- A registration is not an attendance record until check-in is accepted by the backend.
- Enforce at most one initial accepted check-in per attendee registration unless the event explicitly uses entry/exit re-entry tracking.
- For events with re-entry enabled, use transaction-safe state transitions (`OUTSIDE` to `INSIDE` at entry; `INSIDE` to `OUTSIDE` at exit) and append-only gate event history.
- If re-entry is not enabled, repeated scans should show the original check-in and warn staff instead of creating another attendance count.
- Keep attempted scans, accepted check-ins, rejected attempts, and manual exceptions distinguishable in the audit/event log.
- Never show a successful check-in until the backend confirms it.

### Staff interfaces and queue management

Provide distinct modes or stations:
- **Fast check-in:** scan existing QR passes; display attendee name and policy-required verification status.
- **Walk-in registration:** search for an existing registration, create a new one if needed, issue a pass/badge, and check in.
- **Exception desk:** resolve duplicate matches, missing passes, contact-verification problems, failed identity checks, capacity exceptions, and authorized overrides.

Show a clear result such as accepted, already checked in, verification required, invalid/revoked credential, duplicate needs review, or capacity reached. Avoid exposing full contact details on a public-facing scan screen; reveal only what the operator needs.

### Reporting

- Current occupancy if re-entry tracking is enabled.
- Verification status totals, including pending and failed verification.
- Duplicate candidates, rejected scans, manual overrides, and unresolved exceptions.
- Exportable registration and check-in records with role-based access and only necessary personal data.

Do not describe a person as identity-verified unless the required verification actually occurred. Reports should distinguish registered, contact-verified, ID-checked, checked-in, and currently inside.

### Security, privacy, and reliability

- Apply role-based authorization and least-privilege access to attendee personal data.
- Protect public registration and verification endpoints with rate limiting, input validation, anti-abuse controls, and safe error responses.
- Use opaque QR credentials and never encode names, emails, phone numbers, or ID information in QR payloads.
- Use server timestamps, database transactions, idempotency, and concurrency protection to prevent duplicate registrations/check-ins and inconsistent occupancy.
- Avoid displaying full email/phone values on gate screens or in logs.
- Define a retention policy for event registration, verification, and attendance data; restrict exports and record sensitive administrative access where appropriate.
- Provide a clear process for correcting a person's details, revoking/replacing credentials, and handling deletion or retention requests according to the organization's policy and applicable law.
- If offline scanning is supported, explicitly design durable local records and synchronization/conflict handling; do not claim global duplicate prevention while scanners are disconnected.

### Acceptance criteria

1. An admin can configure an event's advance-registration, walk-in, capacity, re-entry, and verification policies.
2. Advance attendees can register and receive a QR credential without creating a general account.
3. Staff can register walk-ins, search for likely duplicates, and issue a paper badge/pass.
4. An attendee without a phone can still be registered and checked in.
5. Every admitted attendee has an event registration and an accepted check-in record.
6. Reports distinguish online registrations, walk-ins, contact verification, ID checks, check-ins, and current occupancy.
7. Contact verification is never presented as proof of legal identity.
8. Required ID verification cannot be silently bypassed; authorized overrides require a reason and audit entry.
9. Duplicate scans and retries do not inflate attendance counts.
10. Existing volunteer attendance and international participant access remain functional, with additive migrations only.
11. Staff can resolve exceptions without creating unnecessary duplicate identities or collecting unnecessary identity-document data.
12. Authorized admins can export event records and review verification/attendance audit history.
