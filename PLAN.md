# Implementation Specification: Volunteer Attendance System

## 1. Objective

Build a QR-based volunteer attendance system for an organization that conducts multiple activities and sessions at different physical locations, primarily on weekends.

The system must allow any registered, active volunteer to check in to an eligible session by scanning a **printed, static QR code displayed at the venue**.

The system records only:
- Which volunteer attended which session.
- The server-recorded date and time of their tap-in.

Do not implement employee-style attendance, payroll, mandatory volunteer assignments, working hours, or automatic absence tracking.

## 2. Core Product Principles

1. Attendance is session-based, not employee-day-based.
2. Any registered, active volunteer can attend any session that permits general volunteer participation.
3. Each venue has a reusable, printed QR code.
4. A venue QR identifies the venue; it does not authorize attendance by itself.
5. A volunteer can have only one attendance record per session.
6. A volunteer may attend multiple sessions on the same day, generating a separate record for each session.
7. Attendance timestamps must be generated by the server.
8. Closed and cancelled sessions must reject ordinary check-ins.
9. All administrative corrections must be auditable.
10. Do not create missing-attendance records for volunteers who did not attend.

## 3. User Roles

### Volunteer
- Register and sign in.
- Scan a venue QR code.
- View the venue and eligible sessions.
- Select a session and confirm attendance.
- View successful check-in confirmation.
- View personal attendance history.

### Administrator
- Manage volunteers.
- Create and manage venues.
- Generate, download, print, revoke, and replace venue QR codes.
- Create, publish, open, close, reopen, and cancel sessions.
- View session attendance in real time.
- Search attendance records.
- Correct attendance records with a mandatory reason.
- View volunteer participation history.
- Export session attendance reports.
- Review an audit log of administrative actions.

## 4. Venue QR Code Lifecycle

Each venue must have a unique, reusable QR code.

### QR generation
- Generate a QR code when a venue is created.
- Encode a URL such as `https://your-domain.example/check-in/v/{opaque-venue-id}`.
- Use a unique, non-sequential venue identifier.
- Do not encode volunteer credentials, session permissions, or reusable authentication secrets.
- Allow the admin to download and print the QR code.
- Display the venue name and basic instructions alongside the QR.

### QR usage
- A volunteer scans the printed QR code.
- The QR opens the venue-specific attendance page.
- The backend verifies that the venue exists, is active, and has a valid QR configuration.
- The system identifies sessions currently accepting check-ins at that venue.

### QR revocation
- Admins can revoke a venue QR if it is compromised or the venue is deactivated.
- Revoking a QR must immediately prevent new check-ins through that code.
- Admins can generate and print a replacement.
- Existing attendance records must not be deleted when a QR is revoked.

The QR is a venue identifier, not proof that a volunteer is physically present. Do not claim that static QR scanning alone prevents proxy attendance.

## 5. Session Lifecycle

Implement the following session states:

- `DRAFT`: Session is being created or edited; unavailable for check-in.
- `SCHEDULED`: Session is published but its check-in window has not opened.
- `OPEN`: Session is accepting attendance.
- `CLOSED`: Ordinary check-ins are no longer accepted.
- `CANCELLED`: Session has been cancelled and cannot accept attendance.
- `ARCHIVED`: Session is retained for historical reference.

### Session fields
- Session ID.
- Activity title.
- Optional description.
- Venue ID.
- Scheduled start time.
- Scheduled end time.
- Check-in opening time.
- Check-in closing time.
- Session status.
- Created by.
- Created and updated timestamps.

### Session rules
- Each session belongs to exactly one venue.
- A venue can host multiple sessions.
- Multiple sessions at the same venue may overlap.
- The admin can publish, cancel, close, and reopen sessions according to their permissions.
- Automatically open sessions at their configured check-in opening time.
- Allow authorized admins to open a session early.
- Allow admins to close sessions manually.
- Optionally auto-close sessions at a configured fallback time.
- Closed sessions can be reopened only by an authorized admin.
- Cancelled sessions cannot accept new attendance.
- Archiving must preserve all attendance and audit records.

### Default timing
Use these as configurable defaults:
- Check-in opens 15 minutes before the scheduled start.
- Check-in closes 60 minutes after the scheduled start.
- Admins can adjust these values per session.
- Use the venue's configured time zone for session scheduling.
- Store timestamps in UTC and convert them for display.

## 6. Volunteer Check-In Workflow

Implement this exact workflow:

1. Volunteer scans the printed venue QR code.
2. The system opens the venue-specific attendance page.
3. If the volunteer is not authenticated, require sign-in and then resume the check-in flow.
4. Validate that the venue exists, is active, and has not had its QR revoked.
5. Fetch sessions at that venue that are currently accepting check-ins.
6. If no sessions are available, show: "There are no activities currently accepting attendance at this venue."
7. If one session is available, preselect it.
8. If multiple sessions are available, display a session selection screen showing:
   - Activity name.
   - Venue.
   - Scheduled start and end times.
   - Any short description needed to distinguish activities.
9. The volunteer selects the correct session.
10. Display a confirmation screen identifying the selected activity and venue.
11. The volunteer presses "Confirm attendance."
12. The backend revalidates the session, venue, volunteer account, QR configuration, and check-in window.
13. If valid, create the attendance record using the server timestamp.
14. Return a success response and show the activity name, date, venue, and tap-in time.
15. If the volunteer has already checked in, return the existing record and its original timestamp instead of creating a duplicate.

The frontend must never display a successful check-in until the backend confirms it.

## 7. Attendance Data and Rules

An attendance record must contain:

- Attendance record ID.
- Session ID.
- Volunteer ID.
- Server-generated `tapped_in_at` timestamp.
- Source, such as `QR` or `ADMIN`.
- Creator or actor ID where applicable.
- Creation and update timestamps.

### Database constraints
- Enforce a unique constraint on `(session_id, volunteer_id)`.
- Use foreign keys for session and volunteer relationships.
- Reject attendance for inactive volunteers.
- Reject attendance for invalid venues, revoked QR codes, closed sessions, and cancelled sessions.
- Reject ordinary check-ins outside the configured check-in window.
- Generate timestamps on the server.
- Use transactions and idempotent request handling to prevent duplicate records during retries or concurrent requests.

Do not store a daily attendance status for every volunteer. A volunteer who did not attend simply has no attendance record for that session.

## 8. Admin Attendance Dashboard

Provide a session-focused dashboard.

### Session list
Show:
- Activity name.
- Venue.
- Date and time.
- Session lifecycle status.
- Number of volunteers checked in.
- Quick actions to view, edit, close, cancel, or manage the session.

Include filters for date range, venue, activity name, and session status.

### Session detail page
Show:
- Activity details.
- Venue and scheduled times.
- Current session status.
- QR status and QR management actions.
- Total unique volunteers checked in.
- Searchable attendance list.

Each attendance row should show:
- Volunteer name.
- Volunteer identifier.
- Tap-in time.
- Record source.
- Available administrative actions.

Do not show "absent volunteers" or "not checked in" for the general volunteer directory. Volunteers are not assigned mandatory attendance obligations.

### Manual corrections
- Require an explicit reason for each correction.
- Record the admin's identity and timestamp.
- Preserve the original timestamp and values in the audit history.
- Do not silently overwrite historical data.
- Apply the same duplicate and session-consistency constraints to manual records.

### Reports and exports
Allow admins to export session attendance as CSV, including:
- Activity name.
- Session date.
- Venue.
- Volunteer name.
- Volunteer identifier.
- Tap-in timestamp.
- Record source.

Also provide a volunteer history page listing all sessions attended by that volunteer.

## 9. Security and Reliability

Implement the following controls:

- HTTPS for all production requests.
- Authentication and authorization on every protected endpoint.
- Role-based access control for administrative functions.
- Server-side validation for every attendance submission.
- Rate limiting for repeated failed requests.
- QR revocation checks.
- Database uniqueness constraints and transaction-safe attendance creation.
- Idempotent retries for network timeouts.
- Audit logs for session changes, QR revocation, attendance corrections, and administrative actions.
- Safe handling of expired sessions and invalid venue identifiers.
- No secrets or authentication credentials embedded in QR codes.
- Do not trust client-provided timestamps or session statuses.

### Network failures
If the network is unavailable, do not claim attendance has been recorded. Show a clear retry option or direct the volunteer to an admin-assisted process.

If the server saves attendance but the response times out, a retry must return the existing record rather than create another one.

### Static QR limitations
A printed QR can be photographed and shared. Authentication and QR validation do not prove physical presence.

Keep the MVP simple. Additional verification, such as supervised check-in, can be considered later if the organization needs stronger protection against proxy attendance.

## 11. API Requirements

Implement equivalent endpoints using the project's existing conventions.

### Volunteer
- `GET /check-in/venues/{venue_id}` — retrieve venue information and currently available sessions.
- `POST /check-in` — record attendance for a selected session.
- `GET /volunteers/me/attendance` — retrieve the authenticated volunteer's attendance history.

### Admin: venues and QR codes
- `POST /admin/locations`
- `GET /admin/locations`
- `PATCH /admin/locations/{id}`
- `POST /admin/locations/{id}/qr-codes`
- `POST /admin/qr-codes/{id}/revoke`

### Admin: sessions
- `POST /admin/sessions`
- `GET /admin/sessions`
- `GET /admin/sessions/{id}`
- `PATCH /admin/sessions/{id}`
- `POST /admin/sessions/{id}/publish`
- `POST /admin/sessions/{id}/open`
- `POST /admin/sessions/{id}/close`
- `POST /admin/sessions/{id}/cancel`
- `POST /admin/sessions/{id}/reopen`

### Admin: attendance
- `GET /admin/sessions/{id}/attendance`
- `POST /admin/sessions/{id}/attendance` — manually add attendance when authorized.
- `PATCH /admin/attendance/{id}` — correct an attendance record.
- `GET /admin/volunteers/{id}/attendance`
- `GET /admin/reports/attendance.csv`

These are proposed API contracts, not a requirement to duplicate routes if the existing project already has equivalent endpoints.

## 12. Error Handling

Return clear, actionable responses for:

- Unauthenticated volunteer.
- Inactive volunteer account.
- Unknown or deactivated venue.
- Revoked QR code.
- No currently available sessions.
- Invalid session selection.
- Session not yet open.
- Session closed or cancelled.
- Duplicate check-in.
- Network timeout or server error.
- Unauthorized administrative action.

For duplicate check-ins, return the existing attendance record as a successful, idempotent outcome.

For other validation failures, do not create an attendance record.

## 13. Acceptance Criteria

The implementation is complete when all of the following are verified:

1. An admin can create multiple venues.
2. Each venue has a printable, reusable QR code.
3. Revoking a venue QR immediately blocks new check-ins through that code.
4. An admin can create multiple sessions at different venues.
5. Multiple sessions can exist at the same venue, including overlapping sessions.
6. A registered volunteer can scan a venue QR and select an eligible session.
7. An unauthenticated volunteer must authenticate before attendance is recorded.
8. A successful tap-in records the server timestamp.
9. Scanning twice for the same session does not create duplicate attendance.
10. The same volunteer can attend two different sessions on the same day.
11. Sessions reject ordinary tap-ins before their check-in window and after closure.
12. Cancelled sessions reject new attendance.
13. Network retries do not create duplicate records.
14. Admins can view attendance and export session reports.
15. Volunteers can view their own attendance history.
16. Manual corrections require a reason and generate an audit record.
17. A volunteer who does not attend has no attendance record; no absence record is created.
18. QR scans, venue identifiers, and client-provided timestamps cannot bypass server-side validation.
